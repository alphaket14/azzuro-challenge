# Azzurro Hotels — Review Intelligence Platform

Collects Booking.com guest reviews for four Azzurro Hotels properties and
gives non-technical operations staff a dashboard to monitor sentiment,
compare property performance week over week, and spot recurring
operational issues (cleanliness, check-in, staff behaviour, noise,
facilities, location, room condition, value for money).

- **Scraper**: Python + Playwright + BeautifulSoup → SQLite
- **Backend**: FastAPI REST API over that SQLite data
- **Frontend**: Next.js + React + TypeScript + Tailwind + Recharts

See [docs/architecture.md](docs/architecture.md) for a diagram and the
reasoning behind the stack choices.

---

## Quick start (demo mode — no live scraping required)

This is the fastest way to see the whole thing working, using the
committed sample dataset (`data/sample_reviews.json`) — see
**"Important: how the sample data was produced"** below for why this is
synthetic rather than live-scraped data.

```bash
# 1. Install everything (Python venv + deps, Playwright browser, frontend deps)
make install

# 2. Seed the local SQLite DB from the committed sample dataset
make seed

# 3. In one terminal: start the API
make backend      # http://localhost:8000 (docs at /docs)

# 4. In another terminal: start the dashboard
make frontend     # http://localhost:3000
```

Open `http://localhost:3000` — you should see KPI cards, a property
breakdown, operational insights with headline callouts, a trend chart, and
a filterable review feed, all populated from the seeded data.

Requirements: Python 3.11+ and Node.js 18+. `make install` creates a
`.venv/` and a `frontend/node_modules/`; neither is committed.

## Running the real scraper

```bash
source .venv/bin/activate
python -m scraper.run --properties all --max-pages 20 --export-json data/sample_reviews.json
```

Key flags:

| Flag | Purpose |
|---|---|
| `--properties all\|id1,id2` | Which properties to scrape (ids: `olympic-paddington`, `venus-potts-point`, `venus-surry-hills`, `chateau-de-venus`) |
| `--max-pages N` | Hard cap on pages scraped per property |
| `--force-full-rescan` | Disable the incremental "stop after N already-seen reviews" optimization |
| `--headless` / `--no-headless` | Run Chromium headless (default) or visibly, useful when debugging selector drift |
| `--delay-min` / `--delay-max` | Seconds to randomly wait between page loads (politeness) |
| `--export-json PATH` | Also write newly collected reviews to a JSON file (merged with existing entries) |

After a run, check `scraper/logs/scrape_<timestamp>.log` for a full log,
including a dedicated stream of per-field parse warnings, and read the
printed summary (new / duplicate / parse-failure counts per property, and
any hard errors).

**Important: how the sample data was produced.** During development, the
scraper above was run against the real, live Booking.com pages for all
four properties. It correctly navigated to each property page and
triggered the "Read all reviews" interaction — but Booking.com's
bot-detection/challenge system intercepted the session at that point
(requests to `/__challenge_.../mp_verify`, `/__challenge_.../telemetry`,
etc. were observed firing instead of review content loading). This is
exactly the "Booking.com may block/rate-limit/CAPTCHA automated access"
risk this project set out to handle honestly, rather than something
hypothetical.

Given that, `data/sample_reviews.json` (the committed sample-data
deliverable) was generated by `scripts/generate_sample_data.py` instead: a
script that produces realistic, schema-accurate reviews and runs them
through the **exact same** hashing/classification/sentiment code
(`common/hashing.py`, `common/topics.py`) that the live scraper uses, so
the rest of the pipeline (DB schema, dedup, backend aggregation, frontend)
is exercised identically to how it would run on real scraped data. **This
sample data is synthetic, not scraped, and is clearly scoped to this
script/file** — the scraper code itself (`scraper/`) is real, working
Playwright automation, not a mock.

If you run the scraper from an environment/IP that Booking.com doesn't
challenge, it should collect real reviews using the same code path; the
scraper and demo-seed paths converge on the identical database schema (see
`docs/architecture.md`).

## Review collection method, reliability, and limitations

**Approach**: a headless Playwright/Chromium session navigates to each
property's Booking.com page, dismisses the cookie banner, opens the
reviews panel, attempts to sort by "Newest first", and paginates through
review cards (`scraper/pagination.py` tries a `?page=N` URL pattern first,
falling back to clicking a "load more"/next-page control if that doesn't
change the visible content). Each review card is parsed defensively
(`scraper/parser.py`) — every field is extracted in its own try/except, so
a missing optional field (reviewer country, room type, length of stay)
never drops the whole review; only a review with no extractable text at
all is skipped (and logged).

**Deduplication**: each review gets a stable key —
`sha256(property_id + reviewer_name + review_date + full_text)` — since
Booking.com does not expose a public review id. Reviews are treated as
immutable; if the hash already exists, it's skipped.

**Incremental updates**: with reviews sorted newest-first, the scraper
stops paginating a property after 5 consecutive already-seen reviews
(`common/config.CONSECUTIVE_SEEN_THRESHOLD`), so re-running the scraper
periodically only costs a few pages of requests rather than a full
re-scrape. `--force-full-rescan` disables this for a full backfill.

**Error handling**: page loads retry up to 3 times with exponential
backoff; each property is wrapped in its own try/except so one property's
failure (or a CAPTCHA block) never aborts the others; the CLI exits
non-zero only if every property failed outright. All selectors live in one
file (`scraper/selectors.py`) as fallback-chain lists, so a Booking.com
markup change only needs a new candidate selector there, not a code change
scattered across the scraper.

**Known limitations**:
- **Booking.com actively blocks/challenges automated browsers** — observed
  directly during development (see above). No CAPTCHA-solving, proxy
  rotation, or anti-detection techniques are used; this is a deliberate,
  documented "best effort" scope boundary, not an oversight.
- Selectors were written against Booking.com's markup as observed at build
  time (November 2026) and may drift; the fallback-chain design in
  `selectors.py` is the mitigation, but it is not foolproof.
- Fields like reviewer country, room type, and length of stay are
  inconsistently present depending on what the guest/Booking.com chose to
  show, and are stored as `null` when absent.
- Single machine, single IP, no distributed/rotating infrastructure.
- Ratings are stored on Booking.com's native 0–10 scale; `rating_normalized`
  (÷2) is also stored for any future 0–5 display use, but the dashboard
  currently shows the native 0–10 scale throughout for consistency.

## Insights methodology & limitations

Topic classification and sentiment are **rule/keyword-based**, not an LLM
call — see `common/topics.py` and `common/topics.yaml`.

- Each review's text is matched (case-insensitive, word-boundary) against
  phrase lists for the 8 required topics (cleanliness, check-in
  experience, staff/receptionist behaviour, noise, facilities, location,
  room condition, value for money), defined in `common/topics.yaml`. This
  file is deliberately plain YAML with no code, so an operations analyst
  can add or remove trigger phrases without touching Python.
- A review can match zero, one, or several topics. `confidence` is a
  simple heuristic (`matched phrases ÷ configured phrases for that topic`,
  capped at 1.0) — useful for ranking, **not** a calibrated probability.
- Sentiment comes primarily from the numeric rating (≥8 → positive, ≤5 →
  negative, 6–7 → neutral, on the 0–10 scale) and falls back to keyword
  polarity counts when a rating is missing.
- The weekly insight shape (`GET /api/insights/topics`) aggregates
  "% of negative reviews mentioning topic X" overall and per property, and
  generates plain-language headline sentences (e.g. *"40% of negative
  reviews this week mentioned cleanliness-related issues"*) via a simple
  threshold rule (≥25% of negative reviews), not generative text.

**Known limitations**:
- No negation handling — "not dirty at all" still matches "dirty" as a
  negative cleanliness signal.
- No sarcasm detection.
- English-only keyword lists; non-English reviews will be under-classified.
- Multi-topic reviews are tagged with every topic they match, with no
  weighting of which topic is "primary".
- Confidence is a heuristic ratio, not a statistically calibrated score.

An LLM-based classifier (e.g. calling Claude per review) is a reasonable
future upgrade for more nuanced cases, but was intentionally not built for
this deliverable in favor of a transparent, zero-cost, fully explainable
baseline that ops staff can audit and tune themselves via
`common/topics.yaml`.

## Project structure

```
common/      shared Python lib: DB models, dedup hashing, config, topic classifier
scraper/     Playwright scraper (CLI: python -m scraper.run)
backend/     FastAPI REST API over the SQLite DB
frontend/    Next.js dashboard
data/        sample_reviews.json (committed) + azzurro.db (generated, gitignored)
scripts/     seed_db.py, generate_sample_data.py, run_scraper.sh
docs/        architecture notes
```

## Data & privacy

- No credentials, API keys, or cookies are required or committed.
  `frontend/.env.local.example` documents the one configurable value
  (`NEXT_PUBLIC_API_BASE_URL`).
- Reviewer names shown are first-name-plus-initial, exactly as Booking.com
  displays them publicly on the review itself — no private or
  authenticated data is accessed.
- `data/azzurro.db` is gitignored (generated from the committed JSON via
  `make seed`) to avoid committing a binary file that would just be
  regenerated.

## Running tests

```bash
make test
# or: python -m pytest -q
```

Covers the topic classifier (`backend/tests/test_topics.py`) and the
weekly/property aggregation logic (`backend/tests/test_aggregation.py`)
against fixed in-memory data.

## Known issues / assumptions

- Assumes Booking.com's DOM structure and review-panel interaction pattern
  as observed in November 2026; see selector fallback-chain notes above.
- Assumes a Monday–Sunday week definition for "this week" / "last week"
  comparisons (`common` has no explicit week-start config; see
  `backend/app/services/aggregation.py:week_bounds`).
- The committed sample dataset is synthetic (see "How the sample data was
  produced" above) — treat dashboard numbers as illustrative, not as real
  guest feedback for these properties.
